# How Ducky compares

This page sets Ducky 2.0 beside the most widely used state-management options for Blazor: [Fluxor](https://github.com/mrpmorris/Fluxor), the most downloaded Redux-style library for Blazor on nuget.org; [TimeWarp.State](https://github.com/TimeWarpEngineering/timewarp-state), formerly Blazor-State; and the hand-written state container of Microsoft's Blazor docs, with the persistent component state that .NET 10 adds. Every statement about another library links to its documentation, source or issue tracker, and every statement about Ducky links to the guide that shows it.

The snapshot is as of 2026-11-08: Fluxor 6.11.0 (released 2026-08-03), TimeWarp.State 11.0.3 (its latest stable release, 2025-06-20; from beta.9 the 12.0 betas target .NET 11, and they are not compared), and ASP.NET Core 10.0. Ducky 2.0 is a pre-release: it is not yet published on nuget.org. Fluxor has been on nuget.org since 2020 and has years of production use.

The migration guides take an app from each: [Fluxor](migration/fluxor.md), [TimeWarp.State](migration/timewarp-state.md), [a hand-written state container](migration/state-container.md).

## Where the others are ahead

- **Fluxor** runs on .NET 8, 9 and 10, has been released on nuget.org since 2020, and counts over four million downloads of `Fluxor.Blazor.Web`. Its behaviour is known from years of production use; Ducky 2.0's is not yet.
- **TimeWarp.State** needs fewer types for an async operation: one handler awaits and mutates, where Ducky asks for a reducer and an effect. Its stable line runs on .NET 8.
- **A hand-written container** has no dependency at all, and on .NET 10 its prerendered values reach the interactive render with one attribute and one registration. For a few values shared by a few components, it is the simpler choice.
- **Equal:** Fluxor and Ducky both detect a change by reference, both create one effect instance per store, and both build on the same Redux DevTools extension.

## When not to choose Ducky

- **Your app targets .NET 8 or .NET 9.** Ducky 2.0 targets `net10.0` only. Fluxor supports all three.
- **You need a released, proven library today.** Ducky 2.0 is a pre-release.
- **You prefer MVVM.** Ducky is a Redux store. View models with `CommunityToolkit.Mvvm` are a different model, not a migration.
- **Your app is small.** A few values shared by a few components need no store: a state container service, or a cascading value, is less code.
- **You rely on packages built for another library**, such as Fluxor.Persist or Fluxor middleware from the community.
