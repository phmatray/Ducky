# ADR-0011: Browser storage wins over the prerender seed

- Status: Accepted
- Date: 2026-09-30
- Related: SPEC §11.4; SSR-01; matrix conflict 8; review rounds 1, 3, 4, 5, 6 and 7

## Context

When a slice is both prerendered and persisted (browser or Server storage), the seed and storage may disagree. Since .NET 10, the same seed mechanism also carries a paused circuit's live state to the resumed circuit, and that state is newer than browser storage whenever writes failed during the disconnect that preceded the pause.

## Decision

The rule is scoped to **prerender** seeds (envelope `src: "prerender"`): apply the seed synchronously (no flicker), then storage (browser or `IDistributedCache`), which wins if it holds a valid envelope, even an older one, costing one extra render. No timestamp comparison. The order doesn't depend on registration order, host timing or whether the cache completes synchronously: `PersistenceMiddleware` enqueues its restore only after the shared `SeedSettled` signal, which `PrerenderHandoff` completes once the seed restore was enqueued or skipped (in the browser, at the first component registration or after the short `PrerenderSeedWaitTimeout` bound, whichever comes first; `PersistentComponentState.RegisterOnRestoring` is not used, because in .NET 10 it fires at registration and not for the initial restore, so it would settle the wait with no seed, review round 4). A **pause** seed (`src: "pause"`, written by a paused interactive circuit) wins over **browser** storage for the browser-storage keys it carries: their storage restore is skipped and their writers are signalled, so storage is rewritten with the seed value. Review round 5 narrowed it: for Server-storage keys storage wins, as over a prerender seed (a Server write never fails on a disconnect, so the override could only roll back another circuit's newer write); a pause leaves out every key of a hydration attempt still in flight (a scope switch's reset initial state is not data); and scoped keys are captured with a SHA-256 of their scope and applied only when the resumed store's epoch-0 scope matches it, never in the synchronous prefix, so a circuit resumed under another user neither shows nor writes the previous user's scoped slices. Review round 6 narrowed it again: storage is often newer than the pause seed (another tab, or the WASM store of an Auto document, keeps writing the same Local key while the circuit is paused), so the override applies only to keys that were **dirty** at the pause, those whose local serialization differs from `LastKnownPayload` (the last successful write, read or receipt; an absent baseline compares as the initial state), listed in the envelope's `dirty` array; clean carried keys follow prerender precedence. Everything a seed carries (values, left-out keys, scope hash, dirty keys) is derived from one snapshot taken after the idle wait. Review round 7: a pause seed can outlive a deploy (.NET 10 keeps paused-circuit state for hours, precisely so a circuit survives a redeploy), and seed values never go through the storage envelope's version check or migrations, so the seed envelope is `{v, src, scope?, dirty?, ver?, slices}`, where `ver` maps each carried persisted key to its `PersistOptions.Version` when the seed was taken; a persisted key whose recorded version differs from the current one, or is missing, is dropped from the synchronous restore, the `dirty` set and the scoped hand-off, and storage (migrated) or the initial state applies (`Circuit_ResumeAfterVersionBump_DirtySeedKeyDropped_StorageMigrated`).

## Consequences

A uniform, testable rule (`Precedence_ValidStorageEnvelope_WinsOverSeed`, `Precedence_OlderStorageEnvelope_StillWins`, `Precedence_ServerStorage_IndependentOfRegistrationOrder`, `Precedence_PrerenderSeed_StorageStillWins`, `Prerender_WasmAwaitedPreload_WarnsAndDoesNotInvertPrecedence`, `Circuit_ResumeAfterDisconnect_PauseSeedWinsOverStaleLocalStorage`, `Circuit_ResumeUnderOtherUser_PauseSeedScopedSlicesNotRestoredOrWritten`, `Circuit_PauseDuringScopeSwitch_StorageNotOverwrittenWithInitialState`, `Circuit_ResumeAfterOtherTabWrote_CleanKey_StorageWins`, `Circuit_ResumeAfterVersionBump_DirtySeedKeyDropped_StorageMigrated`). Client/server clock skew can't cause surprises, and a circuit resume doesn't roll back to stale storage.

## Alternatives considered

Newest-timestamp wins (rejected: clock skew); prerender seed wins (rejected: loses the user's local changes); relying on registration order for precedence (rejected in round 3: a browser preload can start persistence's read before the seed is taken).
