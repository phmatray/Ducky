Blazor state you can explain to a duck.

Ducky is a small, strict Redux store for .NET and Blazor. Slices, effects, persistence, prerender handoff, cross-tab sync and Redux DevTools follow the same rules in every render mode, and every promise it makes is a named test.

The duck's questions

One dispatcher. One action at a time.

Every action goes through one queue, and a single drainer reduces it. Reducers never run concurrently, actions keep their order, and every committed snapshot comes from one commit, so no reader sees torn state.

await DispatchAsync completes once the action is reduced, so you read your own write. It returns a DispatchResult and never faults.

// generated: store.Dispatch(new Rename("Ada"))
store.Rename("Ada");

// completes once the action is reduced
var result = await store.RenameAsync("Grace");

var name = store.State.Get<Greeting>().Name; // "Grace"

Load once, in every render mode.

Mark the slice Persist<T>() and Prerender<T>(). The prerendered page hands its state to the interactive store before the first interactive render, and your load effect asks one question: was this slice already restored?

The same rule holds on WebAssembly, Interactive Server, Interactive Auto and static SSR.

public sealed class LoadCatalog(ICatalogApi api)
    : Effect<StoreInitialized>
{
    public override async Task Handle(
        StoreInitialized action,
        EffectContext context,
        CancellationToken cancellationToken)
    {
        // Storage or the prerender seed already restored it:
        // don't load it again.
        if (context.State.WasRestored<CatalogState>())
        {
            return;
        }

        context.Dispatch(new CatalogLoaded(
            await api.GetProductsAsync(cancellationToken)));
    }
}

Tabs converge. Nothing echoes.

Turn on SyncAcrossTabs for a localStorage slice and a change in one tab reaches the others. A value received from another tab is never written back, even when two processes serialize the same state in different orders.

Sign out in one tab and ClearPersistedState resets the slice everywhere.

public static DuckyBuilder AddSyncedPreferences(
    DuckyBuilder ducky) => ducky
    .UseJson(DocsJson.Default)
    .AddSlice<PreferencesSlice>()
    .Persist<PreferencesSlice>(options =>
        options.SyncAcrossTabs = true); // localStorage only

The newest request wins. The stale one can't speak.

Effects declare a concurrency policy. With Switch, a newer request for the same key cancels the running one, and a superseded run that ignores its token still can't dispatch: its late result is dropped, typed and counted.

Other keys load side by side.

public sealed class LoadForecastEffect(IWeatherApi api)
    : Effect<LoadForecast>
{
    // A newer LoadForecast for the same city cancels the running
    // one; other cities load side by side.
    public override Concurrency Policy => Concurrency.Switch;
    protected override object? ConcurrencyKey(
        LoadForecast action) => action.City;
    public override Task Handle(
        LoadForecast action,
        EffectContext context,
        CancellationToken cancellationToken) =>
        context.Run(
            started: new ForecastLoading(action.City),
            work: token =>
                api.GetForecastAsync(action.City, token),
            succeeded: forecast => new ForecastLoaded(forecast),
            failed: exception => new ForecastFailed(
                action.City, exception.Message),
            cancellationToken);
}

Proved by INV-11

  • Switch_SupersededRunIgnoringToken_CannotDispatch
  • Switch_OldRunCompletion_DoesNotRemoveNewSlot
  • Switch_SupersededRunCallingSliceStoreSet_IsDropped
  • the full concurrency policy matrix

The whole API fits on one desk.

State is an immutable record. Reducers are pure functions on it. The generator writes the registration and the dispatch helpers, so there is nothing to scan and nothing to wire by hand.

public sealed class GreetingSlice : Slice<Greeting>
{
    public GreetingSlice() => On<Rename>((state, action) => state with { Name = action.Name });

    protected override Greeting Initial => new("world");
}

public sealed class CartStore : SliceStore<Cart> // key "cart"
{
    public CartStore() => On<CheckedOut>(_ => Initial); // still a slice: it reacts to actions
    protected override Cart Initial => new([]);
    public int Count => State.Lines.Count; // a point-in-time read
    public void Add(CartLine line) => Set(cart => cart with { Lines = cart.Lines.Add(line) }); // DevTools: "cart/Add"
    public void Remove(string sku) => Set(cart => cart with { Lines = cart.Lines.RemoveAll(line => line.Sku == sku) });
    public Task<DispatchResult> ClearAsync() => SetAsync(_ => Initial);
}

Prefer methods to actions? A SliceStore is a slice with methods, and still goes through every middleware, persistence and DevTools.

public sealed class BoardSlice : Slice<Board>
{
    public BoardSlice()
    {
        On<CardAdded>((state, action) => state.Produce(draft =>
            draft.Cards.Add(new Card(action.Id, action.Title, Done: false))));
        On<DoneCardsCleared>(state => state.Produce(draft =>
            draft.Cards.RemoveAll(card => card.Done)));
        On<FilterChanged>((state, action) => state.Produce(draft => draft.Filter = action.Filter));
    }

    protected override Board Initial => new([], Filter: "all");
}

Built on .NET 10, not around it.

.NET 10 persists component state across prerender and circuit pauses. Ducky's prerender handoff uses that same mechanism. What Blazor leaves to you is everything around it.

The duck checks the receipts.

The specification states 32 invariants. Each one is enforced in exactly one place and has named tests, and a CI gate runs them on every change. The build fails when any of these breaks.
